One label is not a protocol bound

A system does not inherit a post-quantum security level from the absence of elliptic-curve signatures. Wallet authorization, recursive validity, hash collision resistance and hash preimage resistance contribute different terms. The complete protocol is bounded by the weakest composed result.

The current ledger pins the following values:

ComponentPost-quantum bound
Wallet authorization79 bits
Recursive HistoryStep83 bits
Poseidon2b collision resistance85 bits
Poseidon2b preimage resistance128 bits
Complete protocol floor79 bits

The result is a proven 79-bit post-quantum engineering security floor across the complete consensus proof pipeline. “Engineering floor” is deliberate: it is a parameterized bound for the implemented protocol, not a claim that every possible use of a 256-bit wallet secret has 256 bits of quantum security.

Why the ledger is Rust code

The soundness calculation depends on exact query counts, field size, proximity parameters, oracle output length, challenge scheduling and union terms. Those values already exist in code. Repeating them only in a paper or documentation table creates a second, unauthenticated parameter set.

The ledger therefore exposes a typed structure and release tests:

SoundnessLedger {
    wallet_base_iop_bits: 95,
    wallet_qrom_target_bits: 79,
    history_step_classical_bits: 100,
    history_step_qrom_bits: 83,
    hash_preimage_pq_bits: 128,
    hash_collision_pq_bits: 85,
}

A test checks the complete structure and asserts that post_quantum_floor_bits() returns 79. Parameter validators reject zero queries, invalid radii, the wrong sampling model and attempts to claim a fixed Fiat–Shamir grinding credit.

From a base IOP to the wallet QROM target

The wallet authorization base IOP is budgeted at 95 bits. The QROM accounting includes the public-coin programming budget and oracle-query terms rather than simply halving a classical number. For the selected parameters, the diagnostic random-bad-response term is approximately 79.049 bits before the final conservative integer floor. The published wallet target is 79 bits.

The tests retain the rational form of the base error—field term plus query-miss term—rather than first rounding it to a bit count and then composing rounded values. This prevents a small optimistic rounding from being repeated across terms.

HistoryStep is calculated separately

Recursive HistoryStep has a 100-bit classical soundness budget and an 83-bit QROM bound under the selected query-budget exponent and 128-bit preimage term. It is not assigned the wallet's 79-bit number by analogy. The two calculations share the BCS/QROM accounting machinery but use their own inputs.

Taking the minimum then gives 79 bits. If a future protocol change lowers HistoryStep to 77, the complete floor changes automatically. If wallet authorization improves above 83 while HistoryStep remains fixed, the published floor becomes 83.

Finite batches, not asymptotic shorthand

Large random linear combinations originally used one power ladder. At the maximum batched-Merkle shape, roughly 217 claims could make the finite Schwartz–Zippel term bottom out near 2−111. The replacement expresses each index in base 64 and samples one challenge per digit level:

weight[i] = ∏j cjdigitj(i)

The largest production batch needs three levels. Each level has degree at most 63, so the finite error is at most 189 / 2^128, approximately 2−120.4. Batches of at most 64 claims keep the original single-challenge power ladder and do not pay for extra levels.

Why this matters

The calculation is tied to the maximum implemented batch, not hidden inside an asymptotic “negligible” term. A change to claim count or digit base changes both native and in-trace schedules and is test-visible.

Not every consensus check has soundness bits

Value conservation, slot occupancy, issuance, chainwork comparison and deterministic state transition are exact checks. They can have implementation bugs, but they do not contribute a probabilistic soundness term when evaluated correctly. Mixing them into the same bit table would imply a probability model that does not exist.

The ledger covers proof and hash assumptions. Consensus invariants have their own exact tests and differential checks.

What the number does and does not say

  • It is a lower bound across the currently parameterized consensus proof pipeline.
  • It is post-quantum accounting, not a classical-only estimate.
  • It does not cover endpoint compromise, secret theft or implementation vulnerabilities.
  • It does not turn transparent public values into confidential values.
  • It must be recalculated when a security-critical parameter or transcript schedule changes.

The publication rule

The website and documentation quote the result, but the source remains authoritative. Reviewers can inspect the formulas, selected constants and assertions in the executable soundness ledger. This makes the security floor a value the build checks rather than a sentence that can survive after its assumptions have changed.
