B64 and B255: choosing proof classes from measured cadence

Why two authenticated matrix classes were enough, and why a third class was rejected after measurement rather than intuition.

By O(1) Lab4 min readReproducible benchmark
①

Abstract

The two-class laboratory measured production HistoryStep preparation and verification at the exact B64 and B255 geometries, authenticated the frozen matrix pack, and tested the wallet path from one page to the 1,020-input maximum. The result fixed a small-machine B64 floor and a B255 high-throughput class without adding an intermediate consensus geometry.

The class-count question

A recursive proof system can always add another circuit class. That does not mean it should. Every class adds an authenticated matrix leaf, release artifact, selection rule, test surface and long-lived consensus branch. The B64/B255 study asked a narrower question: can two fixed geometries cover both ordinary machines and maximum block fan-in while keeping the class ladder small?

The answer could not come from row counts alone. It required the production HistoryStep assembler, prover, terminal codec and verifier; the exact frozen matrices; the wallet authorization path; and sustained measurements against the fifteen-second block target.

The two geometries

ClassField shapePhysical user pagesRole
B64m230–64Small-machine production floor
B255m2465–255Maximum block page class

A logical PagedSpend may contain at most 128 pages, 1,020 inputs and 256 outputs. A block may contain at most 255 physical user pages, 1,020 inputs and 510 outputs. Those limits are not a third proof class: the same fixed parent representation covers both m23 and m24.

Rejected branch

The laboratory explored an A128 middle class, capsule transposition and a Merkle forest. Those experiments were removed when measurements showed that the launch ladder could return to the existing B64/B255 geometries. Keeping the extra class would have preserved complexity without establishing a necessary operating region.

One capsule across 1,020 inputs

The wallet benchmark measured page construction, logical hashing, one unchanged witness-hiding capsule, atomic-intent encoding and decoding, and local capsule admission. Network latency and HistoryStep proving were excluded.

The capsule median stays around two hundred milliseconds while page hashing and intent bytes grow with fan-in. That is the intended invariant: inputs owned by the same secret do not create one zero-knowledge authorization proof per page.

Production HistoryStep measurements

The first twenty-sample run used an Intel Core i7-1365U with AVX2 and VPCLMULQDQ, no AVX-512, under an active desktop session. The benchmark authenticated the frozen two-entry pack, constructed an honest recursive B64 parent and measured the production HistoryStep path. Parent construction, wallet-capsule generation, PoW search and durable block commit were setup or out of scope.

The B64 median had 2.826 seconds of margin but the sustained p95 missed the target by 182 milliseconds. B255 needed 2.134× more complete-prepare throughput to place its p95 at fifteen seconds. The machine was therefore a valid B64 functional floor and not a B255 host.

A code-generation experiment, not a protocol change

The next run changed only release code generation: thin LTO and one codegen unit. The relation, witness, matrix pack and benchmark methodology were unchanged.

B64 prepare p50 improved from 12.174 to 11.472 seconds and p95 from 15.182 to 14.387 seconds. B255 improved too, but remained outside the laptop class. Profiling placed almost all time in PCS commitment and the post-commit recursive phase, not PagedSpend or networking.

Reproducing the authenticated pack

Proof timing is not enough if a release depends on generated matrices. The laboratory regenerated the complete B64/B255 pack from an empty output root and compared the runtime metadata and both matrix leaves byte for byte.

  • generation time: 5,596.2 seconds;
  • B64 compressed leaf: 4,584,391 bytes;
  • B255 compressed leaf: 11,912,603 bytes;
  • runtime metadata: 1,732,922 bytes;
  • complete pinned pack: 18,229,916 bytes.

The fresh generation matched the recorded digests. This turned “the matrices can be rebuilt” into a release check rather than an assumption.

The decision

The measured boundary supported two conclusions. First, B64 is a real lower hardware class only when the release profile and thermal conditions keep its tail under cadence. Second, B255 is a distinct high-throughput class; pretending it can run on the same laptop would make the class label meaningless.

Most importantly, no measurement established a need for a third class. The two-leaf ladder remained smaller, easier to authenticate and easier to reason about.
